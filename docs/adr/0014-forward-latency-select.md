# ADR 0014：端口转发多目标按延迟自动选择

状态：已定案，实施中（agent 部分已完成；进度见 `docs/plans/forward-latency-select.md`）
日期：2026-11-16
关联：ADR 0005（native 转发、整表重建、域名重解析）、0006（dnat 规则只读）、0010（Mac 客户端 AppKit）、0013 决策 8（客户端只做 Mac）

## 背景

一条 native 转发只能指向一个目标，目标挂了转发就断，只能手动改。用户要 agent 探测目标存活并自动切换；讨论中用户把「主备切换」改成「按延迟自动选择转发哪个地址」。

用户到 agent 这一段走哪个目标都一样，差别只在 agent 到各目标这一段，所以 agent 本机测 TCP 握手耗时就是该比的量。

## 决策

| # | 决策 | 理由 |
|---|------|------|
| 1 | 一条规则可挂多个目标（host + 端口，端口段形状与监听段的约束同现有 `dest_port`），**不分主次**；只有一个目标的规则行为与现在一致 | 用户拍板只做按延迟，不保留固定优先级模式 |
| 2 | 同一时间只用一个目标，新连接全部 DNAT 到它；**不做负载均衡** | 用户拍板 |
| 3 | 探测：每 5 秒对每个目标做一次 TCP connect（超时 2 秒），握手耗时为一次样本；延迟取最近 6 次成功样本的中位数 | 中位数抗单次抖动 |
| 4 | 探测端口默认取目标端口段的第一个端口；纯 UDP 规则**必填**一个 TCP 探测端口（用户拍板），延迟也按它测 | UDP 没法用 connect 判活；ICMP 只能看机器在不在，且常被云禁 |
| 5 | 连续失败 3 次判挂、连续成功 2 次判恢复；挂的目标立即踢出候选，约 15 秒切走 | 故障切换不等延迟比较窗口 |
| 6 | 延迟切换要求另一目标**连续 60 秒**比当前目标快 20% 以上**且**至少快 10ms | 延迟相近的两台不来回切 |
| 7 | 全部目标都判挂时停在最后在用的目标，规则不撤（用户拍板） | 撤规则比打一个可能恢复的目标更糟 |
| 8 | 切换 = 重算选中目标后走现有 `apply_now` 整表重建；已建立连接按 conntrack 里的 NAT 绑定继续走原目标 | 复用 ADR 0005 流程；切换不断线 |
| 9 | 因目标判挂而切走时，agent 经 netlink（ctnetlink）删掉回程源为该目标 IP:端口的 conntrack 记录；因延迟切换时不删 | 持续发包的 UDP 流会不断给 conntrack 续期，不删就永远卡在死目标上；不依赖服务器装 `conntrack` 命令 |
| 10 | 域名目标先解析再探测解析出的 IP；禁区检查（`forbidden_forward_target`）照常对每次解析结果生效 | 与 ADR 0005 安全闸一致 |
| 11 | 探测参数、阈值写死，不开配置项 | 没人要调 |
| 12 | 只对 native 规则；dnat 来源规则只读，不支持多目标 | ADR 0006 |
| 13 | 客户端只做 Mac 原生（AppKit），移动端（Tauri）不动 | 沿用 ADR 0013 决策 8 |

## 展示

`ForwardView` / `UnifiedForwardView` 增 `extra_targets`、`probe_port`，以及每个目标的状态（`targets`：存活 / 判挂 / 未探测、延迟中位数、是否当前在用）和规则级的 `last_switch`（时间、原因、前后目标下标）。旧 agent 会忽略请求里的额外目标、静默按单目标保存，客户端在保存后核对返回的规则，发现额外目标没保存就提示升级（客户端拿不到 agent 版本，无法事先判断）。

选中目标与上次切换持久化在 `state.json` 的 `failover`（重启后流量不跳回目标 0；`resolved` 始终是选中目标的 IP）。健康与延迟只在服务进程内存里，重启后从「未探测」重新攒；所以 `ipgate-agent forwards`（独立进程）只能列出各目标、标出当前在用的和上次切换，看不到实时延迟。

## 已否决

- **固定优先级主备**（主目标活着就一直用、恢复后切回）：用户选只做按延迟。
- **多健康目标之间负载均衡**：用户拍板不做。
- **纯 UDP 规则用 ICMP 判活**：只能看机器在不在，服务挂了看不出来，且有的云默认禁 ping。
- **依赖 `conntrack` 命令清连接**：多数服务器没装，没装时 UDP 切换实际不生效。

## 已知限制

- 周期重解析在落地锁内做域名解析；DNS 不通时，同一时刻的 API 落地与探测切换要排队等它，最多晚几十秒（状态不会错）。探测本身每轮 4 秒截止，没按时回来的目标记一次失败，不会拖慢别的目标的判挂。
- 清 conntrack 按「目标 IP:端口 + 监听端口段」过滤，不区分入口网卡：两条不同网卡、同监听端口、同目标的规则，一条判挂切走会顺带清掉另一条到该目标的连接（客户端重连即可）。dump 期间表在变时可能漏删（未处理 `NLM_F_DUMP_INTR`），漏掉的 UDP 流要等下次判挂。

- 目标被选中时，agent 自己的探测连接也会命中 postrouting 的 SNAT（源改成入口网卡 IP），与真实转发流量走同一条路；目标回不了这个源地址时会被判挂，这正是转发本身也不通的情况。

- 因延迟切换时，已建立的长连接（含持续发包的 UDP 流）继续走旧目标，只有新连接走更快的目标。
- 测的是 TCP 握手耗时，反映 agent 到目标的往返，不反映目标的带宽和负载。
- 旧客户端（不认识多目标）编辑多目标规则会把额外目标清掉：不写兼容代码，Mac 客户端与 agent 一起升级。
- 降级到旧 agent 会忽略额外目标，规则退回单目标，之后一保存额外目标就丢了。

## 验证

- 2026-11-16 OrbStack 特权容器（rust:1.92-slim-trixie，arm64，nft 1.1.3）跑真 agent：一个客户端 netns、两个后端 netns（TCP/UDP 回显自身名字），规则 `--proto both --dest b1 --alt b2`。
  - b1 断网后 15 秒判挂切到 b2，清掉 3 条 conntrack 记录；固定源端口持续发包的 UDP 流随即改由 b2 回包；agent 自己的探测连接记录未被误删。
  - b1 恢复、b2 加 60ms 延迟后约 80 秒按延迟切回 b1（样本窗口 + 60 秒持续期）。
  - `forwards` 正确标出在用目标与上次切换；nat 表只含选中目标。
- 同日按独立审查修了三处状态一致性问题（编辑规则后回退 IP 取自旧目标的探测记录、改目标列表时解析缓存残留旧选中目标的 IP、探测期间规则被删改仍写入切换）后复测，结果相同。
- 同日补测延迟切换不打断已建立的连接：b1 一开始就加 60ms 延迟，切换前先建一条持续收数据的 TCP 长连接和一条固定源端口的 UDP 流；约 60 秒后按延迟切到 b2，长连接照常收数据、对端仍是 b1，UDP 回包仍来自 b1，切换后的新连接走 b2。
- 未验证：x86_64、el7（nft 0.8）、真机内核、域名目标的实际重解析、DNS 卡住时的 4 秒截止。
